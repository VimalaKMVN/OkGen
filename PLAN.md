## 1. What it is
A visualizer/editor for fixed-width **"OK files"** — the label-print data files
TJX DCs feed to NiceLabel. Every field sits at an exact character position/size;
hand-editing them in a text editor is slow and breaks easily. OkGen shows
friendly per-section forms (coded values as plain-English labels), guarantees the
file round-trips **byte-for-byte**, and adds bulk operations + one-click send to
NiceLabel. Pure **Python (Flask)** + vanilla-JS SPA. Runs **local & offline** on
Windows (double-click `run.bat`).

**Salient value (use for demos/marketing):** (1) pain-free editing of one file,
then *at scale* — 100/day; (2) **bulk everything** — bulk edit, bulk rename that
keeps filenames in sync with content, Make Unique; (3) **one-click Send to
NiceLabel**.

## 2. Architecture (the seam that matters)
```
Browser (vanilla JS)  web/templates/index.html · static/app.js · static/styles.css
   │ JSON /api/*
Flask (thin wrapper)  web/app.py
   │ plain Python
Service (REUSABLE, framework-agnostic)  api/service.py   ← all real logic lives here
   │
Core engine  okfile.py (byte-exact parse/serialize) · detect.py · config.py · layout/*
```
The service layer is HTTP-free on purpose, so a React/Node front-end could swap in
later with no core rewrite. (Note: a stale docstring in `service.py` still says
"FastAPI" — the actual web layer is Flask.)

### Key files
| File | Role |
|---|---|
| `src/okgen/okfile.py` | Byte-exact parse/serialize; records hold raw bytes, edits overwrite only a field's span |
| `src/okgen/detect.py` | Layout detection from marker + header position rules |
| `src/okgen/config.py` | Loads all `config/*.yaml`; typed accessors |
| `src/okgen/layout/*` | Compile `.xlsx` layout defs → JSON; registry, validate, models |
| `src/okgen/api/service.py` | Every operation: tree, parse, edits, record add/move/delete, file ops, bulk_*, rename_*, make_unique, send_to_nicelabel, browse_folder |
| `src/okgen/web/app.py` | Flask routes (`/api/*`) |
| `src/okgen/web/static/app.js` | The whole SPA (tree, editor, bulk, rename, send animation) |
| `src/okgen/cli.py` | `okgen compile|detect|parse|serve` |
| `run.bat` / `run.cmd` / `run.sh` | One-click launch; offline install from `vendor/wheels`. `run.cmd` is an identical copy of `run.bat` for environments that strip `.bat` files in transit (AV/DLP) — see README |

### Domain facts
- **Banners (chains):** 01 TJMAXX · 02 Marshalls · 03 HomeGoods · 04 Winners · 05 Europe (EU) · 06 HomeSense (`config/chains.yaml`).
- **Layouts:** CartonLabel · DistLabels · Preticket · StyleHeader (NA, fixed-width) · **EUPreticket** (EU/EWMS, **pipe-delimited + UTF-8 BOM**) · **EUStyleHeader** + **EUCartonLabel** (EU/EWMS GTA, **pipe-delimited, Latin-1, no BOM**; every line leads with `|`). Detection keys off the char at the marker-adjusted header position (`|`/`#`/`&` first char shifts xls Position +1): `N`→StyleHeader, `Y`→Preticket, `C:`→CartonLabel, `7`/`9`→DistLabels; **UTF-8 BOM + `¦P|`→EUPreticket** (checked first); **`|`-led + format letter at raw pos 2** `D`→EUStyleHeader / `H`→EUCartonLabel.
- **Unique key per layout:** CartonLabel=`picklist_id` · DistLabels=`keytrol` · Preticket=`po` · StyleHeader=`keytrol` · EUPreticket=`po` · EUStyleHeader=`keytrol` · EUCartonLabel=`keytrol` (`config/keys.yaml`).
- **Config-driven:** `config/*.yaml` — chains, display (coded→label rules), field_colors, keys, limits, section_counts, nicelabel (hot-folder path + warning + quips/done_quips), rename_tokens, rename_presets. Tests use decoupled `tests/fixtures/config/`.

## 3. Decision log (durable — the "why")
| # | Decision | Why |
|---|---|---|
| D72 | **A label glues to its value EXCEPT the key, and a derived field gets a `<name>_code` companion for filenames.** `K_` keeps its separator on all 10 layouts; `format_code` carries the bare code off a derived value while the field itself keeps its full wording. | Two exceptions that prove their own rules. D69 glued labels because the separator was pure length — true until the value is long and unpunctuated: a Calgary WMS key is a 17-character ASN, and `KS403821608940739A` reads as one undifferentiated run with no visible boundary, which is the readability the gluing was meant to buy. The rule stays; the key is where it inverts, and only the label-to-key join opens — what follows the key is still part of it. The derived-code half is a question of WHOSE value it is: a derived `format` exists as a display string for the editor and as a lookup key for a TOSCA workbook column, so shortening the FIELD would have paid for a filename with two other consumers' correctness. Adding a companion token keeps one value with two renderings and puts the split in the only place that wants it. It is duplicated from `tosca._format_code` rather than shared, at the user's explicit scoping — the same trade as the duplicated Explorer P/Invoke, where a confirmed-working path is worth more than three deduplicated lines; the cost is that two split rules could drift, which is why both are pinned by tests. |
| D71 | **A rename preset names the KEY by its token, never by the field behind it.** Every shipped preset uses `key`, which resolves each FILE's own unique field; a test forbids `keytrol`/`po`/`picklist_id` appearing in any preset. | Naming the field is right only for the layout that uses it, and wrong SILENTLY everywhere else: the field is empty, D69 drops the label with it, and the result is a well-formed filename missing the one value that identifies the order — indistinguishable by eye from a correct one. The failure needs no user error to reach, only a folder holding more than one layout and a single preset applied to it, which is the ordinary way bulk rename is used. **24 of 49 combinations lost the key.** What makes the fix free is that `key` already had to be layout-aware for its own sake (D62's SCAN/WMS resolution), so routing the presets through it changed **no correct-preset name at all** — measured byte-for-byte on all seven diagonals before claiming it. The general rule this is an instance of: where a token resolves a property PER FILE, a preset should say the property, not the field that happens to hold it on one layout — the same reasoning that made `brand_short` read the badge's own source rather than a second copy of it (D68). |
| D70 | **A rename token may name its SECTION (`Details.type`), and the qualified form is offered only where the bare name is ambiguous.** Every field resolves under `Section.field` as well as its bare name; the palette carries the qualified entry only for names that appear in more than one section, and offers it whenever the bare name is offered. The bare name keeps meaning the header's field. | The resolver fills header-first with `setdefault`, so a shadowed field was unreachable BY NAME — and the case that mattered was not obscure: a Calgary `type` is the document discriminator in the header and the ticket type digit on the detail row, so the only spelling available wrote `styleHeaders` into a filename. Nine names collide on that one layout and NONE collide on any `.OK` layout, which is the whole shape of the problem: it is structural to the JSON engine, so the fix is structural rather than a token per collision. Offering only the ambiguous ones is what keeps it proportional — a palette that qualified all 90-odd fields would be twice the size and no more capable, since an unambiguous name already resolves. Deriving the offer from the BASE name's permission means `field_display`-style config keeps listing FIELDS and never learns about sections, so a new layout gets this free. Leaving the bare token pointing at the header is the compatibility half: every existing preset and every other surface in OkGen already reads `type` that way, and a token that quietly changed meaning per layout would be worse than one that is merely incomplete. |
| D69 | **A filename LABEL belongs to the value beside it: glued to it, and dropped with it when there is no value.** `_build_name` resolves parts into glued RUNS; a run whose value slots are all empty is dropped whole, a run with any value survives, and a run of pure literals is always kept. CUSTOM tokens are what mark a part as a label. | Gluing was asked for (`K550000`, not `K_550000`) and it immediately exposed the rest: the old builder skipped an empty value but LEFT THE GLUE FLAG SET, so the next part joined with no separator — `CP` with no compare-at price plus `RP599` became `CPRP599`, which reads as one token and is worse than the `CP_RP_599` it replaced. Dropping the orphan label is the other half and is the D43 rule arriving in a new place: a segment that carries no information should not appear at all, because a reader cannot tell a label with a missing value from a label whose value is legitimately part of the next thing. The run boundary is what makes it safe to be aggressive — dropping on ANY empty part would take a StyleHeader's key away when only its `suffix` is missing, so the rule is *all* value slots empty, not any. Needing to know which tokens are LABELS is why `literal_tokens` is threaded through: without it the rule cannot distinguish `CP` (says nothing alone) from a Text part the user typed deliberately. **Generation passes an EMPTY label set on purpose** — it has never resolved custom tokens, and handing it the real set would start resolving labels that have always come out blank, which is a rename change leaking into generated output. |
| D68 | **A filename token may be SHORT without being lossy — the short form is the one already shown elsewhere.** `brand_short` reads `chains.yaml`'s `short` (the tree badge text); `layout_short` reads the new `config/layout_codes.yaml`; `sl` is a per-batch serial padded to the batch's own width. `brand`, `layout` and `seq` are unchanged. | "Too long" is a real cost — these names are read in Explorer, in the NiceLabel hot folder, and against a 260-char Windows path limit (D44) — but shortening by inventing abbreviations would cost recognition. Reusing the BADGE text means the short form is one a user has already learned from the tree, and means a filename cannot disagree with the badge beside it, because both read one field. The layout codes are config so the EU/NA question stays answerable without code: they currently SHARE codes (`EUStyleHeader` -> `SH`) because the brand badge already carries `EU`, and an unlisted layout falls back to its full name rather than to a blank — D43's silent-empty-segment failure. **The padding is the non-obvious half**: a serial exists to order files, and unpadded it orders them `1, 10, 11, 2` in exactly the two tools that consume them, so an unpadded "1, 2, 3" would have satisfied the request and defeated its purpose. Sizing the pad to the BATCH rather than to a constant is what keeps the two goals from fighting — correct sorting at any size, and no name longer than its batch requires. `seq` is left alone precisely because it is not a rename token only: Volume Generate stamps it on files it creates, so widening or narrowing it would rename generated output as a side effect. |
| D67 | **A suggestions list must be browsable on a field that already HOLDS a value — which `<datalist>` cannot do, so the dropdown is built in `app.js`.** An `<input>`, a ▾ button and a menu in one positioned `.fval-wrap`: ▾ shows every value, typing filters by substring, each row carries its label and `code`/`name` tag, and a first row `---- or type value ----` clears the box. **Supersedes D66's mechanism**, keeps its intent (one control, labels on the options, the escape hatch). | D66 removed the `pick…` `<select>` as "two controls for one job" and kept the datalist. That was backwards: a datalist filters its options by the box's current content, by PREFIX, so on a populated field — and these fields are always populated — the list collapses to the value already there and offers nothing. Chrome/Firefox show nothing until the user edits the text; Safari shows only values, never labels. **The `<select>` was the half that worked** (it shows every option regardless of value), so the refactor deleted the working control and kept the broken one. The deeper lesson is about the TESTS, not the widget: D66's suite asserted the options existed in the DOM and every check passed, because a DOM stub cannot model the browser's filtering — so *"the options are present"* was never the same claim as *"the user can see them"*. Every check now starts from a POPULATED field, which is the condition under which the old design fails; an empty-box test passes against both. Building the menu also removes the browser variance entirely, which is what makes Safari and Edge behave alike after a defect reported on one of them. |
| D66 | **A field whose option list is SUGGESTIONS renders as one control — the box's own dropdown — with the labels on the options and a first entry that clears it.** The `pick…` `<select>` beside a freeform field is withdrawn; its datalist options gain `label` (+ matching text) when label ≠ value, and a first option `---- or type value ----` carries that text as its LABEL with an empty `value`. | Two controls for one field, and the second could not show the field's own value — its first entry had to be a placeholder — so it read as a rival input that might disagree. The box was already an `<input list=>`: the dropdown was there all along, and the picker's only unique contribution was the LABEL for a code, which belongs on the options. **The hint must ride in the label, and that is the whole design**: a chosen suggestion always inserts the option's VALUE, and that insert is subject to `maxLength` — 9 on `chain`, **1** on a detail line's `type` — so a 23-character hint carried as a value would arrive truncated to nonsense, while an empty value fits every field AND inserting it is exactly the "clear the box so I can type" behaviour wanted. Browsers differ on the display half (Firefox shows the label in place of the value, Chrome/Safari show both), which is why the text is set as well as `@label` and why nothing depends on either being rendered. *Found doing it:* `freeform:` is matched by field NAME with NO section scope, so the declaration for the header's document discriminator also governs `CalgaryStyleHeader.Details.type` — a coded 1–9 enum turned into a text box by name collision, and one that `_assert_layout_stable` does not guard (that covers the DOCUMENT type) nor `enforce_options` (§6). That field is also what proves the labels matter: its dropdown was a bare `1..9`. |
| D65 | **A JSON field with no declared width is UNDECLARED, not unlimited — so declare it.** `CalgaryStyleHeader.Sizes.size` is declared **6**, the same width as the `.OK` StyleHeader's own `Size.size`, and a test asserts the two agree so a future spec edit cannot drift them apart. | The spec is built from vendor samples and every sample carries `"size": null`, so there was nothing to measure and the field was left sizeless. `Field.size` on a JSON layout is a MAXIMUM, not a pad width (D20/D48) — but *absent* is not *infinite*, and each write path invented its own answer: Bulk Edit refused (`has no fixed width`), the editor accepted any length, and **Volume Generate skipped the field silently while reporting success**, so a generated batch carried `size: null` with nothing on screen saying so. That last one is why this is a defect and not a papercut — it is the D28/D43/D47 silent-no-op class in the path that CREATES files. Taking the width from the `.OK` engine rather than inventing one is the load-bearing choice: there a size IS the format, so 6 is the real constraint, and it makes the two engines answerable to one number. **The editor is deliberately TIGHTENED** — it alone used to save a 7+ character size — because a field accepted in one panel and refused in another reads as a bug (D63), and the fix must not leave the inconsistency pointing the other way. *What the verification showed about the class:* the silent skip is still there for every OTHER sizeless JSON field (`lane`, `date`, `pageNumber`, the null-width header fields) — declaring one width fixed one field, not the class (§6). |
| D64 | **An emptied section's row may carry a value the HEADER still holds — declared per array, never inferred.** New `empty_row:` block on an array in `ok_to_json.yaml`, applied after the shared `json_empty_rows.yaml` default so it wins per field. Rules are the ordinary ones (`from`/`transform`/`raw`, or an outright `value`) plus **`from_section`** (default `Header`), since by definition the value cannot come from this section's own rows — there are none. Declared for `StyleHeader.sizes[].quantity` <- `Header.tot_qty`, through the same `strip_zeros` a populated row uses. | D46 established that an `.OK` section with no rows must not inherit the template's — that is another order's data. True, and it left `quantity: null` on a StyleHeader with no size lines, which is the *opposite* error: **"no rows" does not mean "no value"** when the header still carries one. `tot_qty` on a size-less file IS the printed quantity — the same thing D58 settled from the `.OK` side, arrived at through conversion — so null threw away the file's only number. Reusing the populated row's transform is what makes the empty row indistinguishable in FORM from a real one (`"22"`, not `"0000022"`); **`size` stays null** because there is no size to recover and inventing one is D33's forbidden silence, which is also why the value is reported with its source (`Header.tot_qty`) rather than appearing unattributed. A zero or blank total is copied through as `"0"` at the user's explicit call, so the rule has no exception to remember — and the case is narrower than it looks: **OkGen's own save can never leave a zero there**, since D58 seeds a blank/zero total 5–10, so a converted `"0"` only comes from a file that ARRIVED carrying one (§6's un-flagged-zero thread, which now has a second consumer). *The deliberate cost, stated not discovered:* D46 shares `json_empty_rows.yaml` between conversion and the JSON engine's own emptying, so "an emptied section looks the same however it got that way" — this breaks that on one field, because only conversion has an `.OK` header to read. A converted size-less file carries `"22"` where a JSON file emptied inside OkGen still carries `null`. |
| D63 | **A detection-signature field whose alternative values are all the SAME layout is EDITABLE.** `DistLabels.format` is removed from `field_display.yaml`'s `readonly:` list; the other six signatures stay. | The lock existed because the field IS the byte detection keys off — but `'7'` and `'9'` **both** resolve to DistLabels, so moving between them changes the ticket format, not the layout, and the lock blocked a legitimate edit on every path at once (the user could not set Coordinate Dist. Label anywhere). The distinction that makes this safe is that the lock was never what protected the file: `readonly` is a UI hint no write path enforces (D51), and the two guards that DO run are value-based, not list-based — `enforce_options` (D60) refuses anything outside the file's own chain list, and `_assert_layout_stable` refuses anything that would stop the file detecting as DistLabels. Measured both directions: `7`/`9` save and still detect as DistLabels, `N` would detect as **StyleHeader** and `8` as **no layout at all**, both refused with the file byte-identical. Unlocked **everywhere** rather than in bulk alone, because the three panels read one list and a field editable in bulk but greyed in the editor reads as a bug rather than a rule. The other six stay locked on the same test: their alternatives are OTHER layouts. *What this shows about the tests:* five of the seven new tests pass on the OLD code too — bulk could always WRITE `7`/`9` and always refused `N`/`8` — which is precisely the proof that unlocking a control widened nothing about what may be saved. |
| D62 | **A property that belongs to a FILE must be asked of the file, even by a screen that groups BY LAYOUT.** `bulk_scope` resolves SCAN/WMS per file (one header read serving both the badge and the key) and locks **every field that is a key for any file in the selection**, each naming which files it is the key for; the panel states the SCAN/WMS split beside the layout. | Bulk Edit built one field list per layout, so it asked `config.unique_field(layout)` with no source at all and got the configured DEFAULT (WMS) for every file — reported as "Style Headers and Distribution Labels show the key as headerASNid even on SCAN orders". The grouping was the cause: the tree, the editor and Volume Generate all pass a path and were always right, and bulk was the one screen with no file in hand at the moment it asked. **The damage was not the label.** On a SCAN selection the greyed field was `headerASNid` — not the key there — while `keytrol`, the field that IS the key, was offered as editable, so one apply would have written an identical key into every file: the uniqueness violation the exclusion exists to prevent, delivered by the exclusion pointing at the wrong field. A MIXED selection is the case a per-layout answer cannot express at all, and it decides the design: `keytrol` is a real key for the SCAN files and an ordinary field for the WMS ones, bulk writes one value to all of them, so both must be locked — and each must say which files it is the key for, since "the unique key" alone would be false of half the files for each of them (D61's true-reason rule under a selection rather than a single file). The source is stated in the panel because on these two layouts it is what DECIDES which field is greyed; a `.OK` layout and CalgaryCartonLabel keep the original one-line reason, because a reason naming a source would be false for them. |
| D61 | **A control the user may not use is SHOWN, greyed, with the reason it is blocked — and the reason must be the true one.** Locked fields appear in Bulk Edit and Volume Generate carrying `editable: false` plus a `locked_reason`, disabled in the panel and refused server-side regardless. Three distinct reasons, not one: `read-only — it identifies the layout` (a detection signature), `assigned automatically — every file gets a unique key` (the key), and `this chain is isolated — it cannot be changed to another group` (D9). The chain's reason travels from the VIEW, the only layer that knows which case applies. | Omitting a field the user cannot edit makes it read as **missing**: hunting for DistLabels' `format`, you cannot tell "OkGen forgot it" from "you may not change it", and the second is a fact worth stating. The reasons are separated because a wrong reason is worse than none — an isolated chain is not a detection signature (detection does not key on the chain at all), and the key is not read-only, it is *handed* a value per file. *Corollary found while writing it:* a test helper taking `header_fields[0]` began asking to randomize a signature the moment locked fields entered the scope — it had depended on an implicit contract that the list held only editable fields, which is exactly the sort of assumption that surfaces only when the contract changes. |
| D60 | **A field's option list becomes the WHOLE TRUTH on every write path — but only when it is declared so.** New `enforce_options:` in `field_display.yaml` (`"*": [format, ticket_format]`); a value outside the list is refused in the single editor, both bulk paths and Volume Generate, resolved against the file's OWN chain. | A ticket format of `8` — which no chain declares — saved cleanly on **all nine layouts** that expose the field and only failed later at NiceLabel; the lists had lived in `display.yaml` since the beginning with nothing enforcing them. Resolution is per chain because formats are per banner (`X` is a Dumbbell Gum Label on Homegoods and a Purple Rat Tail on Winners), so a global list would accept a format wrong for this file. **Opt-in per field is the load-bearing half**: the opposite hazard is worse than the one being fixed — enforcing an INCOMPLETE list refuses legitimate work, which happened immediately when the fixture's `A, B` list rejected the `v0.75.0` `Q`/`X` formats. So a field earns enforcement, `chain` and `type` stay out (isolation and the detection guard already govern them, and their lists are deliberately suggestions — D56), and the refusal names the allowed values so a missing entry is diagnosable. Generation is checked too, and was the worst case: a numeric RANGE on `format` emitted `3, 3, 7` on a letter-format layout, creating invalid files with nobody typing anything. |
| D59 | **Field edits and ROW operations are different kinds of bulk work, and only the first can be batched.** Bulk Edit splits into *field values* (many fields, every section, one apply) and *rows & sequences* (`unique` / `add` / `keep`). Every control maps onto an op that already existed — one value or a comma list -> `list`, a range -> `random`, a date range -> `random_date` — so nothing new can be written. Per file: opened once, all ops applied to that copy, saved once; **all-or-nothing**, with per-field reporting. | Field edits are **order-independent** (each writes a different field), so they can share one apply and a grid can enforce "each field at most once". Row ops are not: *keep 0 rows* then *set qty* writes nothing. That difference is what lets the field panel drop the Operation dropdown and show every section at once, and it is why mixing the two would need an order the UI cannot express. One write per file rather than per field is not just speed — 12 files x 3 fields was 36 writes and 36 `.bak`s. All-or-nothing matters because a **half-updated file is indistinguishable from a correct one** by looking; files stay independent so one bad file never blocks a selection. *Two lessons landed on this work itself:* the new path called `_apply_bulk_op` directly and so skipped the roll-up wrapper `v0.78.0` had just added — D30 arriving through a NEW parallel path rather than an old one — and the same path had no chain-isolation check, which turned out to be missing from the bulk **op** route generally, the fourth appearance of that class. |
| D58 | **A header field may be the SUM of a detail section — and when that section is EMPTY the same field is authoritative instead.** New `config/rollup_fields.yaml` (`field` <- sum of `section`.`source`, plus `seed_when_empty`), applied by `_apply_rollups` at the **five** write sites. Declared for `StyleHeader.tot_qty` <- `Size.qty`. The control is **never locked**: with rows present the sum WINS on every write path, so a typed value is accepted and then corrected, with the save reporting what it changed. With **no rows** the field is left byte-for-byte — deleting the last Size row KEEPS the total — and only a blank/zero one is seeded (random 5–10, once). A sum too wide is **refused, not truncated** (D40); a non-numeric row quantity is an `EditError`, not a silent zero. Opening a file **writes nothing** — the mismatch is badged and corrected on save, ~~or by an opt-in **default-OFF** toggle,~~ or by the `total_qty_scan` bulk sweep, which **previews before it writes** and reports the no-rows files largest-first. *(**The at-open toggle was WITHDRAWN in `v0.79.0`** — one global browser setting cannot mean "my files but not someone else's", and a setting unsafe to leave on does no work. The sweep is now the only route that writes without a Save.)* | The rule post-dates the files: the reference sample declares `tot_qty` 22 against four rows totalling **8**, so this changes data rather than repairing drift. That is why *when* it runs is the whole design. Recomputing at open would rewrite **field content** in a file the user only looked at — the one thing byte-exactness has never done (D26 normalises junk, never a value) — and with every legacy file mismatched it would fire on all of them at once; hence write-time, with the at-open variant opt-in and defaulted OFF (auto-clean can default ON precisely because junk is not data). Enforcing the VALUE rather than locking the control is D51/D56 arrived at from the other side: a lock is a UI hint no save path checks, and it blocks legitimate typing — which is exactly what "type is not allowing me to edit" was. **The empty-section case is the load-bearing half and it inverts the rule**: the new system emits many files with no size lines at all, where `tot_qty` is the printed quantity, so a blanket "recompute from the rows" would write `0000000` over real quantities on the shape that will be most common — D34/D39's borrowed/absent-data class reaching through a *derived* field. It also decides the seed: a random 5–10 fills a blank, but re-rolling on every save would make one file show a different quantity each time and a generated batch unreproducible (D46/D49's "invent nothing silently"), and re-seeding after a delete would discard a real number. Wiring all five write sites rather than the editor is D30; the boundaries tested are D43/D47's (none / one / all-deleted, and BOTH directions). *`size_rec` is deliberately NOT included — the user's call, the new system ignores it — so it stays stale on a single-file add/delete as before.* **Found doing it:** the JS DOM stub could not match attribute selectors, so `.fval[data-section="0"]` matched nothing and any assertion about a live-value lookup would have passed whether or not the lookup worked — the `setAttribute`-no-op class from D56, still latent in `refreshDerived`, which uses the same selector shape and has no suite. |
| D57 | **A JSON `chain` accepts a CODE or a brand NAME in any capitalisation, on every write path — and Europe is still refused.** `chain` widened 2 -> 9 on `CalgaryStyleHeader` and `CalgaryDistLabel` (already 9 on `CalgaryCartonLabel`) and declared `freeform` (D56) on all three, so the editor offers a text box with the codes and names suggested.
